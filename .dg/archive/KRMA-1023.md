## Objective

Choosing Share (the toolbar export/share button) in the Edit workspace presents the macOS sharing menu. It never shows "Share unavailable: no window to present the sharing menu" in the status line when a window is open.

## Context

The user saw the status text `Share unavailable: no window to present the sharing menu` at the bottom left of the Edit view (below the filmstrip) when trying to export. **It came from an earlier build** (About box showed Version 0.1, `aef050e8`, 47 commits behind `main`). `ExportWorkflowCoordinator` was reworked since by KRMA-1000 (`10d830f5`, `f98dcf91`), so this may already be fixed or may not be a real defect. **Update 2026-10-15: the user confirmed the problem still occurs in a current `swift run` build**, so it is not fixed by KRMA-1000. Note `swift run` is the unbundled dev launcher; also check whether the bug reproduces in the packaged Xcode app.

The message is set in `ExportWorkflowCoordinator.presentSharePicker` (around line 446) when `shareAnchorView` is nil, or its `window` is nil. `shareAnchorView` is a `weak var` assigned from `ShareAnchorView.swift`. Likely causes to check:

- The anchor `NSView` is deallocated or detached when the toolbar item is rebuilt (workspace switch, Library to Edit), so the weak reference goes nil.
- The anchor is assigned before it is in a window, and is never re-assigned in `updateNSView`.
- The share render finishes after the anchor has left the window (the picker is presented after async rendering).

Also note that the failure path discards the rendered share file and gives only a status-line message. If it can still happen, consider falling back to the key window or a toolbar-anchored view rather than failing.

### Comment — claude @ 2026-10-15T05:38:29.732Z

Cause: toolbar content can be instantiated more than once, and the last-assigned anchor NSView (set in makeNSView/updateNSView) could be a copy never attached to a window. Fix: ShareAnchorView now registers itself only in viewDidMoveToWindow (and unregisters on leaving), and presentSharePicker falls back to the key/main window content view instead of discarding the share. Replaced the 'never falls back' test with fallback tests (they skip when no key window is available, as under headless CI; I could not run them with a window). swift build clean; scripts/ci-tests.sh fast ran with no failures shown (I only saw the tail of output). Not verified in a live swift run or the packaged app.
