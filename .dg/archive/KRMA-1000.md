## Objective

Every accepted single export, batch export, Share render, and original-plus-settings bundle has one owner. Completing an older job cannot clear a newer one. Quit sees all of them.

## Context

Confirmed by source tracing on 2026-10-14. Overlapping exports were not run. `ExportCoordinator` (`Sources/KromoraKit/ViewModels/ExportCoordinator.swift`, around line 283) assigns `singleTask` without cancelling or retaining the previous task. The previous task's `defer` then sets `singleTask = nil`, which can drop the newer handle. `isExporting` is stored state, not "a job exists". Shutdown (around line 485) awaits only the handles currently stored.

The export menu has no active-export check (`Sources/KromoraKit/ViewModels/MenuCommandAvailability.swift`). The sheet guard only blocks a second sheet. After the first sheet closes, another export can start.

Unowned work: original-plus-settings starts an inner `Task` (`Sources/KromoraKit/ViewModels/ExportWorkflowCoordinator.swift`, around line 194), lazy Share registers provider tasks that are not stored (around line 300), and `ExportWorkflowCoordinator` has no shutdown barrier. Share item providers do not return a `Progress` cancellation handle. Quit's `TerminationGuard` (`AppViewModel.swift`, around line 780) includes batch export and imports only. KRMA-946 already shipped that batch/import confirmation; this ticket extends it. Do not remove it.

Required product choice: while any single export, batch export, Share render, or original-bundle job is active, another export/share/bundle command is refused with a visible status, and the active job is left running. Do not build a multi-job queue and do not build an app-wide operation framework. Imports stay on their existing coordinator.

Sibling KRMA-995 changes which document an item exports. Sibling KRMA-1008 threads sharpening into the batch options. Stay out of those behaviors except where a job must snapshot the options it was given.

Parent epic: KRMA-994. Review finding 5.

## Acceptance criteria

- [ ] Each accepted job has an id, a kind, an immutable input snapshot, a task, a cancellation flag, and a terminal outcome. The snapshot is the document, Look, items, and options at start. Later edits do not change that job.
- [ ] A job's completion clears only its own id. A test starts job A, starts job B after A is refused or, if you intentionally replace A, does so only by cancelling A first. The required behavior is refusal: B does not start, A's handle remains, and A's completion does not clear a different id.
- [ ] `isExporting` and menu availability are derived from the registered jobs. Export, Share, and original-bundle commands are unavailable or refused while one of those jobs is active.
- [ ] The original-bundle task and each lazy Share render task are registered. Shutdown cancels and awaits every registered job. A Share provider's completion handle cancels that work.
- [ ] `TerminationGuard` reports a single export, a Share render, and an original bundle, not only a batch. Tests cover quit-during-each-kind at the guard/coordinator boundary (fake presenter is enough).
- [ ] Cancelling during the file write still removes the partial/staging file. Existing batch cancellation cleanup must keep working.
- [ ] `swift build` is warning-free. `scripts/ci-tests.sh fast` exits 0.
