## Objective

Find the failure point in the current Apple Photos import flow and make successful imports reliable and diagnosable.

## Context

During a review of the current build packaged through `scripts/app-store-build.sh`, the user reports that importing from Apple Photos “just fails.” No exact alert text, selected asset, or failure stage was captured, so the root cause is intentionally unknown. Start by reproducing the end-to-end path in the packaged, sandboxed app and record what the user sees and what the underlying framework/storage calls report.

Follow the path from Photos selection and review, through authorization and original-resource transfer (including iCloud availability), decoding, package-backed library insertion, and durable write. Identify the first failed boundary instead of treating a generic error as a diagnosis. A failure should not leave an item that appears imported but cannot be opened or persisted, and a successful import should survive relaunch.

Avoid duplicating nearby completed work: KRMA-991 addressed review-thumbnail failures; KRMA-1035 addressed iCloud transfer progress; KRMA-1037/1038 addressed review transfer retention and incomplete review checks; KRMA-1031 tracks a filename/type mismatch. Recheck those behaviors only as needed to isolate the reported import failure in the present packaged build.

## Acceptance criteria

- [ ] Reproduce the reported failure in the current packaged app and record the exact user action sequence, whether review opened, the selected asset type/availability (local or iCloud-backed), visible error, and the first failing framework/coordinator/storage boundary. Do not invent a root cause when the failure cannot be reproduced.
- [ ] Fix the identified failure so a valid Photos selection completes through durable package-backed library membership and can be opened after import; preserve cancellation, duplicate/mismatch review, and per-item failure reporting.
- [ ] Failures are surfaced with a useful, actionable message and enough bounded diagnostic detail to distinguish authorization, asset lookup/transfer, decode, and package persistence problems without logging private photo contents or sensitive metadata.
- [ ] A failed or cancelled batch does not leave misleading library membership, corrupt package state, or unmanaged temporary/security-scoped resources. Partial success is reported accurately and successful items remain valid.
- [ ] Add deterministic coverage at the boundary that failed, retaining existing provider injection, review selection, cancellation, and persistence coverage.
- [ ] Verify the packaged app's relevant sandbox/Photos authorization path and perform a real Photos-library confirmation when the environment permits. State clearly which live checks were or were not possible; do not substitute `swift run` behavior for packaged-app verification.
- [ ] `swift build` is warning-free and the focused Photos import tests pass; run the relevant CI lanes for any changed AppKit/PhotoKit/render behavior.

## Implementation notes

Treat the reported “fails” as a symptom, not as evidence that the earlier thumbnail issue returned. Compare the app-store packaged build with the exact current import implementation and capture the concrete error before choosing a fix. Keep PhotoKit objects and temporary resource ownership inside their existing providers/coordinators; follow Swift 6 and security-scoped access rules in `CLAUDE.md`.
