## Objective

Count successful edited Share output as a qualifying engagement finish for the existing App Store review prompt, alongside clean edited Export batches.

## Context

- KRMA-1093 added review requests after two clean edited export finishes across launches. It explicitly excludes Share and Copy.
- Share uses lazy `NSItemProvider` file representations in `ExportWorkflowCoordinator`: opening the picker alone does not render or transfer an output. A selected service later requests a representation.
- Kromora can observe whether it rendered a representation and supplied the file to the provider, but it cannot observe whether the external service ultimately delivered it. Treat a successfully rendered edited file representation supplied through the provider completion callback as the measurable Share success.
- Count one share-picker session at most once, regardless of selection size or how many representations the service requests. Copy to Clipboard remains outside this change.
- Share and Export should contribute to the same two-finish threshold. Two successful edited shares qualify; one share plus one edited export also qualifies, provided the existing later-launch rule is met.

## Acceptance criteria

- [ ] A share-picker session records one qualifying finish when its first edited file representation is successfully rendered and supplied to the requesting service.
- [ ] The policy uses the resolved document for each shared item; identity-only outputs do not count.
- [ ] Opening the picker, dismissing it before a representation is requested, a failed or cancelled render, and Copy to Clipboard do not count.
- [ ] A multi-photo share session counts at most once, even when several edited representations are requested. Repeated provider requests for the same session cannot increment the finish count again.
- [ ] Share finishes contribute to the existing qualifying-finish count. After two qualifying finishes across launches, two shares or an export/share combination may request a review, subject to the existing 120-day cooldown.
- [ ] The existing quiet-app gates remain in force. Do not present over the Share picker or a sharing activity, or while a Share render is active; a covered finish is counted without a deferred surprise prompt.
- [ ] A new Share session cancels any pending review delay, consistent with new export activity.
- [ ] Fake-presenter tests cover successful edited Share, identity output, cancellation/failure, picker dismissal without a request, per-session deduplication, mixed Share/Export threshold, and quiet-app cancellation. Tests never invoke StoreKit UI.
- [ ] No custom review UI, Settings toggle, or entitlement is added.

## Implementation notes

- Keep the existing Export behavior from KRMA-1093 intact. Add the Share completion signal at the lazy file-representation boundary, where success and the item document are known; do not count picker presentation as completion.
- The share picker may request multiple files lazily and may not report final external delivery. Count the first successful edited representation per picker session and document this observable boundary in code.
- Preserve the one-second settling delay, later-launch requirement, persisted request cooldown, and shutdown/cancellation behavior.

## Verification

Run the focused Share/Export and review-prompt test suites, then the affected test set for changed files. No system review sheet should be used as deterministic test evidence.
