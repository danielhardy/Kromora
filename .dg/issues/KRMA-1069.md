## Objective

Stop the production app crashing with `EXC_BREAKPOINT` (dispatch queue assertion) when PhotoKit reports original-resource download progress during a Photos import.

## Context

Crash report (packaged app 0.1 (1), macOS 27.2 26B5112a, Apple Silicon host, 2026-10-19 15:39): thread 8 traps on the `com.apple.NSXPCConnection.m-user.com.apple.photos.service` queue:

```
_dispatch_assert_queue_fail
dispatch_assert_queue
_swift_task_checkIsolatedSwift
swift_task_isCurrentExecutorWithFlagsImpl
closure #1 in static PhotosPickerImportProvider.writeOriginal(_:to:progress:)  (PhotosImportCoordinator.swift:206)
thunk for @escaping @callee_guaranteed (@unowned Double) -> ()
-[PHAssetResourceRequest _setupTotalProgressIfNeeded]_block_invoke
-[PLProgressFollower observeValueForKeyPath:...]
... NSProgress KVO ... xpc message_handler
```

Root cause: `PhotosPickerImportProvider` is `@MainActor`, so its `private static func writeOriginal` is main-actor isolated. The closure literal assigned to `options.progressHandler` (a non-`Sendable` `PHAssetResourceProgressHandler` ObjC block) therefore infers main-actor isolation, and Swift 6 inserts a dynamic isolation check at closure entry. PhotoKit invokes the handler from its XPC queue, the check fails, and the process traps. The closure body itself (a `Mutex` and a `Task { @MainActor in ... }` hop) is already written to be thread-agnostic; only its inferred isolation is wrong. Introduced with the iCloud download progress work in KRMA-1035 (`e485decc`, `984155b3`).

Unit tests did not catch it because the `PhotosImportProviding` fake delivers progress from the main actor and never runs the real PhotoKit callback. The trap needs an original that PhotoKit actually downloads (for example an iCloud-optimized asset) so the progress handler fires.

Relevant files: `Sources/KromoraKit/ViewModels/PhotosImportCoordinator.swift` (`writeOriginal`, around lines 195-220), `Tests/KromoraKitTests/PhotosImportTests.swift`, `docs/ENGINEERING_GUIDE.md` (Swift 6 / isolation guidance).
