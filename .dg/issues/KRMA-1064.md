## Objective

Verify that a large disposable library and sustained editing have a stable working set and retain edits on a lower-memory supported Mac.

## Context and reproduction

This owns the 16 GB memory qualification slice of KRMA-1016. It follows the finite session budget in KRMA-1060 and existing multi-photo Share Copy memory work KRMA-1048; do not duplicate their implementation. The review did not reproduce a memory crash. Existing deterministic budgets do not establish whole-process memory behavior under real RAW decoding, Metal presentation, undo recipes, and Photos/Share activity.

Source review: .context/2026-10-19-release-readiness-review.md (reviewed bb01e0c374fb; re-read current code because subsequent work may have landed).

## Acceptance criteria

- [ ] Use a confirmed disposable profile/package and an actual 16 GB Apple Silicon Mac; record commit, signing, macOS, source megapixels/formats, library size, and exact workload.
- [ ] Exercise thousands of library entries and at least 200 distinct edited photos with representative mask/retouch histories, navigation, scrolling, undo/redo, and revisits; include a larger RAW/full-resolution TIFF export and a bounded Share Copy case.
- [ ] Record process memory and relevant working-set counters at declared repeatable checkpoints over multiple cycles. Distinguish cache warm-up from sustained growth and actual OS memory-pressure behavior.
- [ ] Confirm inactive clean state evicts/hydrates, active/dirty edits remain correct, old write acknowledgements do not lose newer changes, and exported/reopened documents match.
- [ ] Cancel an operation and quit/relaunch after the workload; inspect partial files and package validity. Use only safe disposable failure conditions; do not eject an in-use valuable volume or fill the system disk.
- [ ] Record Pass/Fail/Not run with evidence in KRMA-1016 and file specific regressions. Missing hardware is a human/environment requirement, not a pass or a reason to weaken the supported-platform policy.

## Implementation boundaries

No new display-bound latency/Metal capture is authorized by this ticket. Ordinary memory sampling/counters and a supervised interactive workload are sufficient. Do not create fallback behavior for Intel/older macOS.

Read CLAUDE.md and .dg/AGENTS.md first. Target macOS 26+ / Apple Silicon only, Apple frameworks only, Swift 6 without unsafe isolation escape hatches. Preserve unrelated working-tree changes and existing claims. Claim this issue before implementation; work one issue at a time. Verify only the applicable focused/CI lanes; do not run scripts/run-kromora-capture.sh for an ordinary fix or to obtain a new timing number. Use generated/disposable fixtures and never modify a user's active library. Hand off implementation at review through the normal DispatchGraph workflow; do not claim unrun hands-on checks passed.
