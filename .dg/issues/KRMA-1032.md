## Objective

Make a Look (`.cube`/`.look`, starter, imported, or derived) behave as a **base look that the adjustment sliders then adjust**, instead of a final grade that sits on top of the sliders. After this change the render order is: developed source → **Look** → Light/Color/Effects/Detail/ordered adjustments → local masks → crop → vignette → grain.

## Context

### What happens today

The Look is applied after every global slider, so the sliders feed the LUT and the LUT's output is final:

- `RenderPipeline.buildPreLUTImage` (`Sources/KromoraKit/Models/RenderPipeline.swift`) applies Light → Color → pre-LUT effects (Texture/Clarity/Dehaze) → Detail → ordered `document.adjustments`.
- `RenderPipeline.buildImage(preLUT:…)` then calls `applyLUT`, then crop, vignette, and grain.
- `RenderStageFacade.buildFinalStages` documents this as the product's canonical order ("LUT, crop, post-crop vignette, and deterministic grain").
- `CubeLUT.apply(to:intensity:using:)` crossfades graded and ungraded images with `CIDissolveTransition` in the context's working space (linear-ish, not perceptual). That behavior is shipping behavior (ENGINEERING_GUIDE §8.1) and **must not change**.

Reported effect: dragging Exposure, Contrast, or Temperature after picking a Look does not read as adjusting the Look. The Look re-grades the slider output and can clip or re-map it, so the sliders feel like they act on the input to a fixed transform instead of on the graded picture.

### Why changing the order is feasible

A 3D LUT is a per-pixel RGB remap. Moving it earlier needs no new image math, only a change to where `applyLUT` sits in the graph and what depends on that position.

### Things that depend on the current order (the real work)

1. **The pre-LUT prefix cache.** `ProcessingPrefixStage.preLUT` / `ProcessingPrefixCacheKey` (`RenderCacheKey.swift`) and the materialization flights in `RenderEngine.swift` assume everything expensive (including spatial Texture/Clarity/Dehaze) is LUT-independent, so scrubbing LUT intensity reuses the cached prefix. After this change the LUT is upstream of that work, so the LUT identity and intensity must become part of the prefix identity, and the "LUT-only change reuses the prefix" optimization goes away.
2. **Look browser previews.** `LookPreviewRequest.isLUTOnlyChange` (`RenderRequest.swift`) and `RenderEngine.makeLookPreviewCGImage` render each candidate by sharing the base document's pre-LUT prefix. That sharing is only valid while the LUT is downstream of the sliders. Candidates can still share the developed source, but not the graded prefix.
3. **Save as Look / LUT export.** `LookLUTConverter` samples the real graph at cube lattice points, so the sampled cube follows the new order automatically. The `LUTSupportMatrix` text still says the existing Look is "composed into the sampled global transform" and that stage "order is preserved". The entry order and wording must match the new order. A Look plus sliders must still round-trip within `LUTConversionVerification.defaultTolerance` (0.03).
4. **Local masks.** `applyLocalAdjustments` runs after the global pre-LUT work. It stays after the global sliders, so it is after the Look as well.
5. **Cache invalidation.** `RenderPipeline.pixelEpoch` (currently 35) keys the presentation-frame envelope, thumbnails, idle-frame warmer, and engine caches. It must be bumped to 36, with the doc-comment history updated, so no stale frame rendered in the old order is shown.
6. **Docs and comments** that state the order: `docs/LOOKS.md`, `docs/APP_ARCHITECTURE.md` (Look browser row), `docs/ENGINEERING_GUIDE.md` (render pipeline order and §8.1 context), the `RenderStageFacade` header, and the `RenderCacheKey` comments about the prefix.

### Decisions already made (do not reopen without asking)

- **Visual change to existing edits is accepted.** Documents that have both a Look and non-neutral sliders will render differently after this change. `EditDocument`'s schema does not change, and the stored edit revisions still decode. Do not add a per-document "legacy order" flag or a migration. Per `CLAUDE.md` the project does not carry compatibility paths. Call out the visual change in the handoff comment and PR text.
- **RAW develop stays upstream of the Look.** The Look's input is the developed source after RAW develop (and retouch/rotation/geometry, as today). Only the Light, Color, Effects/Detail, and ordered-adjustment stages move to after the Look.
- **Intensity semantics are unchanged**: the crossfade is between the Look's input and its graded output, now computed at the head of the slider chain.
- **No slider-fitting.** This ticket does not convert a Look into slider values. That would only be an approximation and is out of scope.

### Derive Look

`RecipeExtractor` fits its cube against the editor's neutral RAW baseline, with the Look applied over that baseline (`DeriveInvarianceTests`). The new order matches that assumption more closely, because the Look now sees the developed image rather than slider output. Derive's behavior and fit must not change. The existing derive tests must pass unmodified.

## Acceptance criteria

Order and correctness

- [ ] With the Look set and non-neutral Light/Color/ordered-adjustment sliders, the rendered pixels equal `sliders(Look(developed))` and measurably differ from the old `Look(sliders(developed))`. Prove it in a `RenderPipelineTests` case using a clearly non-linear synthetic cube and a known exposure or contrast change on a generated image (no committed fixtures).
- [ ] A document with a Look and neutral sliders renders identically before and after the change within a tight per-channel tolerance (the order is irrelevant when nothing sits on the other side). This guards against accidental changes to the LUT's color-space or crossfade math.
- [ ] Intensity 0 equals no Look. Intensity 1 equals the full Look. An intermediate value uses the same `CIDissolveTransition` blend as today. An unresolved `lutID` still renders without the Look and without failing.
- [ ] Texture, Clarity, Dehaze, and Detail (sharpening, noise reduction) operate on the graded image. Local mask layers operate on top of the full global result. Crop, then vignette, then grain still run last in that order, and vignette and grain still describe the final cropped frame.
- [ ] Preview, comparison, thumbnail, histogram, and full-resolution export all use the new order. A test renders one document through the preview path and the export path and asserts they agree within the existing parity tolerance.

Caching and responsiveness

- [ ] `RenderPipeline.pixelEpoch` is bumped to 36 and its doc comment records the change.
- [ ] The processing-prefix cache key distinguishes Look identity and intensity. Two documents that differ only by Look or intensity never share a materialized prefix. Add an acceptance test next to `RenderEngineProcessingPrefixAcceptanceTests`.
- [ ] Changing a slider reuses the cached developed source and never re-decodes the RAW or standard image. Changing Look intensity likewise re-runs only the graph from the Look onward, not the source decode. Assert this with the engine's existing materialization and cache counters.
- [ ] The Look browser candidates render in the new order, so a candidate thumbnail matches what the canvas would show if that Look were selected on the same document. The shared-prefix shortcut is removed or restricted to the developed source. Update `LookPreviewTests` accordingly.
- [ ] No new fallback, `#available` branch, or concurrency opt-out is introduced. `PackageSettingsTests` still passes.

Save as Look, Derive, and docs

- [ ] Save as Look/LUT with an active Look plus sliders still produces a cube that verifies within `LUTConversionVerification.defaultTolerance`. The support-matrix entry order and wording reflect the new order, and `LookLUTExportTests` covers a Look-plus-sliders document.
- [ ] `DeriveInvarianceTests` and the Derive tests pass unmodified.
- [ ] `docs/LOOKS.md` states the order (the Look is a base look and sliders adjust it). `docs/APP_ARCHITECTURE.md`, `docs/ENGINEERING_GUIDE.md`, and the `RenderStageFacade` and `RenderCacheKey` comments no longer describe the Look as post-slider or as a "pre-LUT" prefix. Remove or rename "pre-LUT" naming where it would now be misleading.
- [ ] `scripts/ci-tests.sh fast` and `scripts/ci-tests.sh serial` pass.

## Implementation notes

- Start in `RenderPipeline.buildImage(developed:…)` and `buildPreLUTImage`. The simplest shape applies the Look to the developed image, then runs the existing Light → Color → effects → detail → adjustments chain on the result. Rename `buildPreLUTImage` (and `ProcessingPrefixStage.preLUT`, `hasPreLUTWork`) to match what the stage now contains. The prefix should now include the Look.
- `hasPreLUTWork` gates prefix materialization on "is there work beyond the developed source". With the Look inside the prefix, an active Look counts as work. Re-check the preview ROI expansion (`expandedSourceROI`, `needsSpatialSupport`): spatial effects now read Look-graded pixels, so the ROI margin logic is unaffected but worth re-reading.
- Keep Core Image graph construction inside `RenderEngine`/`RenderPipeline` per `CLAUDE.md`. `LUTFilterCache` keeps vending cube filters and is not expected to change.
- Performance tradeoff to measure and state in the handoff: Look intensity scrubbing used to be cheap even with Clarity/Dehaze active, because the prefix was LUT-independent. It now re-evaluates spatial effects. If this is a real regression in the deterministic lanes, consider materializing a "developed + Look" stage separately from the effects stage. Do not over-engineer without numbers.
- **Do not run `scripts/run-kromora-capture.sh`** (display-bound, release-time only; see `CLAUDE.md`). Use the deterministic lanes and a window-independent engine test if a number is needed. Cite `docs/TESTING.md` for existing baselines.

### Out of scope

- Converting a Look into slider values, or any per-document order toggle.
- Changes to LUT parsing, interpolation space, the crossfade, bundled starter Looks, or Derive's fitting.
- A new UI control. Only user-visible copy that describes the order needs updating.
