## Objective

Cancelled thumbnail, editor, and frame-read work must keep its concurrency slot and shutdown ownership until the underlying operation actually exits.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`ImageWorkScheduler.cancel` (`Models/ImageWorkScheduler.swift:421`) keeps cancelled `packageIO` jobs in `running` until they finish (to protect the single-writer invariant), but removes thumbnail, editor, and frame-read jobs immediately and fires their terminal callback. The operation may still be inside ImageIO, a GPU wait, or another non-cooperative call, and replacement work starts on the freed slot. `cancelAllAndWait` (line 411) only awaits tasks still in `running`, so it cannot wait for already-removed tasks.

Probe with the thumbnail limit set to 1 and eight gated, cancellation-oblivious operations: `configured=1 peakActual=8 runningReported=0 actualAfterShutdownBarrier=8`. The real thumbnail provider does synchronous ImageIO work after an async hop, so fast scrolling and repeated supersession can exceed the advertised memory/CPU limits. This proves the accounting defect, not an eight-decoder measurement in the real grid.

## Acceptance criteria

- [ ] Physical work ownership is held until the operation returns, for every lane. A cancelled job still counts against its lane's limit.
- [ ] The caller still gets prompt, exactly-once cancellation notification; logical job IDs can be reused immediately (for example via a draining set that counts against physical limits).
- [ ] `cancelAllAndWait` returns only after all physical operations, including previously cancelled ones, have exited.
- [ ] Tests inject non-cooperative operations in every lane and measure entered/exited counts independently of scheduler dictionaries: peak concurrent operations never exceed the configured limit, repeated reuse of one job ID is safe, and the shutdown barrier leaves zero running operations.
- [ ] Existing `ImageWorkSchedulerTests` pass; no regression in queue ordering or eviction behavior.

## Implementation notes

- The code comment calls eager callbacks for thumbnail/editor lanes "historical". Callers that rely on the eager callback to start replacement work must still be notified promptly.
- Do not run display-bound benchmarks for this ticket.
