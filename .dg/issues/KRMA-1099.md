## Objective

Compute the durable `EditDocument.editHash` at most once per distinct document value and serve it to every remaining consumer, off the main actor where the consumer is already asynchronous. Child 2 of the KRMA-954 plan (`docs/RENDER_KEY_PLAN.md`).

## Scope

- Add an in-memory memo (for example a small `DurableEditIdentity` value carried with the document, or a bounded memo keyed by document equality) that returns the byte-identical existing digest. It caches the durable string; it never invents a new scheme.
- Consumers to move onto the memo: `PreviewPresentationCoordinator` (stored-frame classification, canonical writes, `FrameSignature` construction), `EditedThumbnailCoordinator` (signatures and `editedThumbnailRevision`), `IdleFrameWarmerCoordinator`, `LookPreviewCoordinator.CacheKey`, `AutoRunFingerprint.make`/`matches`, `CurrentEditMeasurement` key construction, `AppleEnhancementReference` provenance.
- For async durable writes (canonical preview frame encode, edited thumbnail), compute the digest off the main actor from the `Sendable` document value.
- Persisted identities (`FrameSignature.editHash` in `LatestPreviewFrameStore`/`ThumbnailFrameStore`, `AutoRunFingerprint.documentHash` inside edit revisions, `CurrentEditMeasurement` cache keys, Apple reference provenance) must remain byte-identical: no store, revision, or cache is invalidated by this ticket.
- Add a computation counter to the memo (internal, test-visible) and extend `RenderKeyHashingBenchmark` or a deterministic test to count durable digests per simulated 30-tick drag with the Look strip visible.

## Acceptance criteria

- [ ] At most one durable digest per distinct document value during a 30-tick drag (counter-asserted test), down from several per tick.
- [ ] Main-actor durable-digest time per tick for the large recipe < 1 ms (benchmark before/after).
- [ ] Golden `editHash` test from the sibling ticket (or an equivalent added here if it has not landed) still passes; stored frames from before the change classify `.exact` after it (round-trip test through `FrameClassifier`).

## Rules every change here must keep (KRMA-954)

- [ ] Compute immutable identity once per relevant mutation; never JSON-encode and hash the whole document on every repeated interaction.
- [ ] Session-local caches may use revision or structural keys; durable cross-launch identity keeps a stable digest (`EditDocument.editHash` bytes unchanged — the golden test stays green).
- [ ] Never persist Swift's randomized `Hasher`/`hashValue` output (no file, frame signature, edit revision, report, or string that leaves the process).
- [ ] Do not remove source, Look, or pipeline-version fences (`RenderSourceFingerprint`, Look/LUT content fingerprint, `RenderPipeline.pixelEpoch`, `LocalMaskRenderer.version`, `RenderIdentity.current`, `PresentationFrameEnvelope.storageFormatVersion`).
- [ ] Texture pooling is out of scope (KRMA-963).
- [ ] Report before/after medians from `KROMORA_RENDER_KEY_BENCHMARK=1 swift test -c release --filter RenderKeyHashingBenchmark` for the plain document **and** the large 5-brush recipe, in the handoff comment and in `docs/TESTING.md` (render-key section).
- [ ] A unit test proves equal documents produce equal keys and that an edit to each relevant field changes the key.
- [ ] `scripts/ci-tests.sh fast` and `scripts/ci-tests.sh serial` exit 0.
