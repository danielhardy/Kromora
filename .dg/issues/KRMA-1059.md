## Objective

Produce a concrete retention policy and window-independent evidence that the next implementation ticket can apply without guessing about persistence or undo semantics.

## Context and reproduction

The review found EditorDocumentCoordinator.sessions and sessionRevisions grow for every opened/edited photo; EditHistory caps each history at 100 entries but there is no whole-session budget. This is distinct from the fixed offscreen-thumbnail issue (KRMA-999), bounded diagnostic rings (KRMA-1007), and Share Copy memory work (KRMA-1048). No memory crash was reproduced.

Sessions are correctness state as well as caches: source loading uses session presence/revisions to avoid overwriting in-memory edits; export uses live documents ahead of disk; persistence acknowledgement can arrive while a newer edit remains dirty. An arbitrary dictionary LRU can lose unsaved work or revive stale source results.

Source review: .context/2026-10-19-release-readiness-review.md (reviewed bb01e0c374fb; re-read current code because subsequent work may have landed).

## Acceptance criteria

- [ ] Map all session/revision readers and writers, active undo/grouping, source-adoption fences, batch paste, history restore, export snapshots, and durable-write acknowledgement.
- [ ] Create a deterministic, window-independent retention probe with generated documents containing substantial mask/retouch recipes over increasing photo counts; report retained session/history counts and reproducible memory/estimated-byte evidence without claiming a device-wide RSS guarantee.
- [ ] Record a finite count/byte budget, pinning/eviction rules, and what happens when dirty or accepted in-flight work temporarily exceeds it. Never silently drop unsaved values.
- [ ] Specify active-photo undo preservation, cold reopening of clean evicted photos from durable edits/history, and whether inactive in-memory undo is intentionally limited; document the user-visible contract.
- [ ] Specify how revision fencing remains correct after eviction and when an older write acknowledges after a newer edit; include precise integration points and deterministic test scenarios for KRMA-1060.
- [ ] Write the chosen policy into current architecture/storage guidance or a focused decision record, and update KRMA-1060 with exact defaults and seams. No broad coordinator rewrite is needed.
