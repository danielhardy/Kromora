## Failed behavior
The current focus regression posts key-window notifications and calls the skipped-draw helper directly. It publishes no Original image and has no NSWindow or drawable. The lifecycle regression opens sources directly and does not navigate Library to Edit or leave and re-enter Edit. A live run through the disposable-app workflow showed 33 photos while the generated fixture package contained one photo, so the window was closed before any UI interaction and the run is not valid evidence.

## Expected outcome
A reproducible headless check proves the presentation policy for skipped and real drawables while the window is defocused and after it regains focus, without another user action; real-compositor delivery is a manual release check. It uses only generated fixture data and also covers source switching and Edit re-entry.

### Counterpoint verification blocker

Independent review found that the focus test does not keep the Original render pending while the window loses key status. `PreviewPublicationCoordinator.didPresentVisibleFrame` schedules the Original only after the Adjusted frame has been presented. The test gates all preview requests, waits for only one request, then defocuses before releasing the gate; that first request is the Adjusted render, and the Original request has not yet been queued.

The test's `isPresented` check (`image != nil && pendingDisplayRevision() == nil`) is not evidence of drawable presentation. `pendingDisplayRevision` is cleared by successful command-buffer completion; drawable presentation is reported separately by the drawable presented handler. The test also evaluates the same predicate immediately after `makeKeyAndOrderFront`, so it can pass without observing a new post-refocus presentation. Finally, `FakeRenderEngine` returns one solid image for every source, so the photo-switch/re-entry test confirms requests but cannot detect stale pixels in either pane.

Required correction: hold the baseline request itself while the window transitions from key to non-key; observe actual drawable presentation for both panes while inactive and after a verified key regain, without another action; and distinguish the generated photos or assert the published frame identity so stale panes fail the test. The test must record both real key-state transitions and skip/report unavailable native presentation instead of treating command-buffer completion as visible pixels.

Verification run: `scripts/test-affected.sh OriginalPresentationWindowTests` passed (2 tests, 0 failures), but the suite does not satisfy the focus/presentation acceptance criteria above. No product code was changed and no display-bound benchmark was run.
