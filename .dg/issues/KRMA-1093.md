## Objective

Ask for an App Store rating once a person has finished a real edit and exported it, at a moment when Kromora is quiet. Use the system review prompt (`AppStore.requestReview` / `SKStoreReviewController`). The system decides whether anything appears.

## Context

Kromora is a sandboxed Mac App Store app (macOS 26, Apple Silicon). There is no review prompt today, and the repo has no App Store product id, so a write-review URL is not available here.

The system prompt is the only review UI App Store Review Guideline 5.6.1 allows. A custom “Enjoying Kromora?” alert, a star control, or a pre-prompt is a custom review prompt and will be rejected. The call is a request, not a command:

- In production the system shows the prompt at most three times per app in a 365-day period, and it may show nothing.
- In TestFlight the call has no effect. A TestFlight session cannot prove the sheet.
- In a development build the sheet appears on every call. Tests and `swift run` must not invoke the real API.
- The app cannot learn whether the person rated, chose Not Now, or whether the system suppressed the sheet. Persist “we called the API”, never “they rated”.

The user-facing Export command is a batch, even for one photo. `ExportWorkflowCoordinator.exportDialog()` (menu, keyboard, and the library context menu) calls `ExportCoordinator.batchExportDialog`, which finishes in `performBatchExport` by posting `ExportCoordinator.summary(for:folder:)` after `finishJob`. That method does not call `onExportCompleted`.

`onExportCompleted` fires from the single-file `performExport` path only. In the app that path is Edit in External Editor: the callback runs after the TIFF is committed and before `finishJob`, and `ExportWorkflowCoordinator.exportCompleted(at:)` then `NSWorkspace.open`s the file. A review sheet there would cover the handoff to the other app. Share, Copy, and the original-plus-settings bundle use `runJob` and never call `onExportCompleted`. Share files are temporary and the sharing picker is the person’s next step.

`EditDocument.isIdentity` is the right “they changed something” check. It includes RAW develop, so a white-balance or exposure-only develop counts. `hasVisibleLookEdits` ignores develop and would skip that session.

Sheets that must stay in front of any review prompt already exist: the AppKit export panel (`ExportCoordinator.isPresentingSheet`), SwiftUI sheets on `ContentView` (welcome, tour, shortcuts, Photos import review), feature sheets (derive, selective copy), and error alerts from `presentError`. `FirstRunOnboarding` persists welcome state in `UserDefaults`. `KromoraSettings` is the preferences store; a review request is engagement state, not a setting the person toggles.

`AppViewModel.shutdown()` is the teardown path. A pending prompt task has to be cancelled there. `deinit` is nonisolated and cannot own that work.

StoreKit is a system framework. The current entitlement set in `App/Kromora.entitlements` does not need a new key for `requestReview`. The signed Mac App Store build is the only place a submitted review can exist.

## Approach

Keep the decision in a pure policy and the system call behind a tiny presenter. `ExportCoordinator` stays the render and disk owner.

### When a finish qualifies

One qualifying finish is a completed Export or Export All (`performBatchExport`) where:

- `exported > 0`
- `failed == 0`
- `cancelled == false`
- `photosFailed == 0`
- at least one successfully written item had a document with `isIdentity == false`

A batch is one finish, including a one-photo export. Carry an `editedExportCount` (default `0` so existing `BatchOutcome` call sites keep compiling) from the batch loop, where `itemDocument` is already resolved. Count it only for items that commit.

These completions stay silent:

- Share, Copy, and the original-plus-settings bundle
- Edit in External Editor, including its `onExportCompleted` callback
- Cancelled exports, failed exports, and batches that skipped or failed any item
- A file write whose Photos delivery failed or warned (`photosFailed > 0`), because that session ends on an error
- A batch of untouched originals (`editedExportCount == 0`)

### When the app may call the API

Record every qualifying finish. Call the API only when all of the following are true at the end of that finish:

- The qualifying-finish count is at least 2.
- The current launch is later than the launch that recorded the first qualifying finish. Two exports in one sitting stay silent; the person has come back.
- The last API call was never, or was at least 120 days ago. That spaces attempts across the system’s three-per-year ceiling instead of spending them on one afternoon. Development builds would otherwise show a sheet on every later export.
- The app is active, the key window has an `NSWindowScene`, no export job is running, no AppKit or SwiftUI sheet is up, and no error alert is up.
- Welcome is not pending (`FirstRunOnboarding.shouldPresentWelcome()` is false).

If the finish qualifies but the app is busy, inactive, or sheet-covered, count the finish and do not call. Do not keep a pending flag that fires when a later sheet closes or on the next launch. The next qualifying export asks again. Pulling the person back from Finder, or covering a sheet they just opened, is the interruption this ticket exists to avoid.

After the success status is posted, wait about one second so the save panel has finished dismissing and the status line is readable. Cancel that wait from `shutdown()`, and cancel it if a new export, share, copy, sheet, or alert starts. Then call the presenter once.

### Where it lives

- A small policy type next to `FirstRunOnboarding`, with an injected `UserDefaults` and clock. Keys use a `Kromora.reviewPrompt.` prefix. It stores the finish count, the launch number of the first qualifying finish, a launch counter, and the date of the last API call. It does not write through `KromoraSettings`, and it does not appear in Settings.
- Increment the launch counter once per process from `AppViewModel`’s existing injected defaults. Tests pass a private suite so they do not touch the developer’s real defaults.
- A presenter protocol whose production implementation calls `AppStore.requestReview(in:)` with the key window’s scene. Skip the call when the scene is missing. `SKStoreReviewController.requestReview(in:)` is the older window-scoped form of the same prompt; do not call the window-less `requestReview()`, which is deprecated. The SwiftUI `requestReview` environment action is the same prompt, but the decision sits beside export completion, so the view model calls the presenter rather than a button.
- `AppViewModel` is the only place that joins the batch outcome, busy and sheet state, the policy, and the presenter. Add a settled-success callback from the batch finish. Leave `onExportCompleted` for the external-editor handoff.

## Acceptance criteria

- [ ] A clean Export or Export All of at least one non-identity edit, with no failed, cancelled, or Photos-failed items, counts as one qualifying finish after the job has finished and the success status is posted.
- [ ] The first qualifying finish, and any later qualifying finish in that same launch, does not call the review API.
- [ ] The second qualifying finish, on a later launch, calls the review API once, about a second after the success status, and only while the app is active with a key-window scene and no sheet, alert, or running export.
- [ ] A call is recorded when the API is invoked. Another qualifying finish within 120 days does not call again. A qualifying finish after 120 days may call again, still subject to the same quiet-app gates.
- [ ] Share, Copy, the original-plus-settings bundle, Edit in External Editor, identity-only exports, cancelled exports, partial batches, and Photos delivery failures do not count and do not call.
- [ ] A qualifying finish that lands while a sheet is up, an alert is up, an export is still running, or the app is inactive is counted and does not schedule a later surprise prompt.
- [ ] The pending wait is cancelled by `AppViewModel.shutdown()` and by a new export, share, copy, sheet, or alert.
- [ ] There is no custom rating UI, no Settings toggle, and no new sandbox entitlement.
- [ ] Policy tests cover the gates above with an injected clock and defaults and never present a system sheet. A wiring test uses a fake presenter and shows that a settled edited export on a later launch asks once, and that the external-editor completion does not.
- [ ] `swift build` is warning-free and the focused tests pass. This change does not need `scripts/run-kromora-capture.sh`.

## Non-goals

- A “Rate Kromora” menu item. A command the person clicked has to do something every time, and `requestReview` may no-op. That item would open the App Store write-review URL, which needs a product id this repo does not have.
- Asking on launch, on quit, after import, after Auto, or when leaving Edit.
- Detecting whether a review was submitted.
- Changing export status copy, the save panel, or which files an export writes.

## Verification

Policy tests and one coordinator or view-model test with a fake presenter are the proof. The system sheet is not deterministic in CI, is absent in TestFlight, and appears on every call in development, so a UI test that waits for it is the wrong check.
