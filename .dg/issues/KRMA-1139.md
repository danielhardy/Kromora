## Objective

Bound peak memory while importing a folder of full-size RAW files, so a single import batch cannot exhaust a 16 GB Apple Silicon Mac.

## Context and reproduction

Found during the KRMA-1064 16 GB qualification run (not a hypothetical). Dev build (`scripts/disposable-app.sh`, Release, ad hoc signed, unsandboxed) on `23393201`, Apple M1 Pro 16 GB, macOS 27.0.1. Each run used a fresh empty disposable library package; File > Import Folder, Select All, Import Selected to Library. Process `phys_footprint` sampled every 2-5 s with `footprint -p`; the capped runs killed the app at 9000 MB. Source files were copies of four real ARW files (47/82/120/122 MB) with unique trailing bytes appended so content identity is distinct; the batches are therefore 5x-60x repeats of four sources.

| Batch | Scan peak | Import | Outcome |
|---|---|---|---|
| 3,000 small JPEGs (600 px) | n/a | peak 752 MB, settled 279 MB idle | pass, no sustained growth |
| 20 RAW | 5.1 GB | peak 6.5 GB, settled 1.1 GB | all 20 imported |
| 40 RAW | 5.0 GB | over 9 GB within seconds | watchdog kill at 9.7 GB; all 40 files already copied into the package |
| 60 RAW | 5.2 GB | over 9 GB within seconds | watchdog kill at 9.8 GB; 47 of 60 imported |
| 240 RAW (uncapped) | not measured | about 38 GB footprint (peak 39.9 GB), reported swap about 44 GB | app process exited with 211 of 240 imported; no crash report, no launch.log output, no kernel kill record found |

Observations:

- The scan phase is bounded (about 5 GB peak regardless of batch size). The import phase is not: footprint keeps climbing for the whole batch and only returns after a small batch completes.
- The uncapped run implies very roughly 175 MB of footprint per imported RAW (about 2x average file size). This is an estimate, not a measured per-file figure.
- The threshold on this machine lies between 20 and 40 RAWs per batch. 30 was not tried.
- Not established: whether cost tracks file size or count, whether real distinct RAWs behave the same, whether the signed sandboxed build behaves the same, and the actual cause of the uncapped run's exit.
- Possibly relevant: KRMA-1060 bounds clean editor-session retention and KRMA-1048 bounds Share Copy; neither is known to bound import.

Raw evidence (local, not committed): `~/Dev/krma1064-fixtures/` holds `krma1064-memory-samples.csv`, `cap.csv`, `cap.events` and the fixture set.

## Acceptance criteria

- [ ] Reproduce on the same machine class: importing 240 full-size RAWs in one batch keeps `phys_footprint` under a documented ceiling (state it; for 16 GB it should stay well clear of physical memory) and imports every file.
- [ ] Identify what retains per-file memory across the import batch (decoded images, thumbnail or analysis work, queued tasks) and bound it with a finite budget or backpressure, not a larger machine assumption.
- [ ] Add a deterministic or opt-in measured test through the real import path with a recorded peak-footprint number in `docs/TESTING.md`.
- [ ] Re-run the KRMA-1064 import step and record the result in KRMA-1016.

## Implementation boundaries

Target macOS 26+ / Apple Silicon only, Apple frameworks only, Swift 6 without unsafe isolation escape hatches. No fallbacks for Intel or older macOS. Do not run `scripts/run-kromora-capture.sh`. Use generated or disposable fixtures and never modify a user's active library. Keep import durability and identity behavior unchanged.

### Comment — claude @ 2026-10-27T16:04:27.206Z

Root cause: FileHandle.read(upToCount:) returns autoreleased chunks, and the package importer reads every source (stage copy, clonefile hash pass) inside one worker job, so no autorelease pool drained until the whole batch finished. That is about 2x the batch size in footprint (the ~175 MB/RAW estimate). Reproduced without any UI via the importer alone: 40 RAW -> 7,480 MiB. Fix (b86da726): autoreleasepool per chunk in PortablePackageTransaction.stage(fileAt:) and hashFile, plus PortablePhotoIdentity.contentHash(ofFileAt:). After: 40 RAW 40 MiB, 120 RAW 75 MiB, 240 RAW 130 MiB (M1 Pro 16 GB, debug, importer only). Tests: PortablePackageImportMemoryTests (deterministic sparse-file guard, measured 1,554 MiB retained before the fix; opt-in real-RAW measurement added to the optional lane); results and ceiling recorded in docs/TESTING.md. Checks: test-affected (56 tests) and scripts/ci-tests.sh fast (2,163) pass; ci-tests.sh verify lane audit passes. NOT done: the app-level re-run of the KRMA-1064 import step (File > Import Folder in the disposable app) and recording it in KRMA-1016; that is a supervised GUI run, so the grid/thumbnail/analysis side of import is not re-measured. Residual unexplained linear growth of ~0.45 MB per file in the importer (not chunk retention; ~450 MiB projected per 1,000 files) is noted in TESTING.md.
