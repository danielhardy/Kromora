## Objective

Deliver finished exports to Photos from the committed file instead of reading the whole file into memory on the main actor.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`ExportCoordinator` (`ViewModels/ExportCoordinator.swift:756`) streams encoding to a file, then reads it back into `Data` on its main-actor path for Photos delivery. `PhotoKitDelivery` (`Models/PhotosDelivery.swift:90`) hands the data to PhotoKit. `.mappedIfSafe` helps residency but guarantees neither zero copies nor cheap downstream access, and the open/read is synchronous on the UI call path. PhotoKit execution and peak memory were not measured.

## Acceptance criteria

- [ ] The delivery boundary accepts the committed file URL and uses `PHAssetCreationRequest.addResource(with:fileURL:options:)`; the data overload stays only for callers that own in-memory bytes.
- [ ] The user's exported file is retained (`shouldMoveFile` is not set), and the URL/security-scope grant is held until the change transaction settles.
- [ ] A Photos failure (denied or limited authorization, album failure, cancellation) leaves the completed disk export intact and counted correctly.
- [ ] Fake-delivery tests cover the file-URL path, the failure cases above, and scope lifetime. No large file is read into `Data` on the main actor.
- [ ] Manual check on a real Photos library with a large TIFF/PNG is noted in the ticket (or explicitly deferred to release qualification).
