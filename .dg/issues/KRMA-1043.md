## Objective

Make empty space in Kromora’s top bar behave as a native window-drag region.

## Context

The user cannot drag the window by grabbing the middle of the top bar. They have noticed similar behavior in other windows as well, so the cause may be outside Kromora. First distinguish a Kromora hit-testing/titlebar issue from an OS-wide or system setting symptom; do not assume either diagnosis.

When the app owns the interaction, users should be able to start a normal window move from genuinely empty top-bar space, as they can from native titlebar regions. Controls, toolbar items, text fields, menus, and the crop-mode actions must continue to receive their own mouse events. KRMA-693 and KRMA-512 establish the current macOS 26 window/chrome approach; treat this as a focused drag-region follow-up, not a titlebar redesign.

## Acceptance criteria

- [ ] Reproduce the drag attempt in the current packaged app and record the exact top-bar region and window/workspace state. Compare an empty Kromora region with an interactive toolbar item and a standard macOS titlebar; note whether other apps show the same failure.
- [ ] If app-owned, empty top-bar areas in Library and Edit can start a native window move, including with the inspector open and while crop mode is visible.
- [ ] Toolbar buttons, menus, text entry, share/export anchors, and other controls remain clickable and do not begin window dragging; drags that start on a control keep their existing behavior.
- [ ] Use a native macOS 26+ SwiftUI/AppKit mechanism appropriate to the current window chrome. Do not add broad gesture overlays that steal input or change drag behavior in every content surface.
- [ ] Add a focused regression for the app-owned draggable-region boundary where it can be exercised deterministically; include a live packaged-app drag check and state whether the issue was reproduced elsewhere in the OS.
- [ ] If the failure is demonstrably system-wide and not controlled by Kromora, document that evidence and the remaining app-specific behavior rather than adding an ineffective workaround.

## Implementation notes

Keep the draggable area limited to unused top-bar space and preserve standard titlebar controls and accessibility. Inspect current SwiftUI toolbar/titlebar hit testing before choosing an API. The report that unrelated windows also fail is evidence to investigate, not a reason to alter system settings or claim an app bug without reproduction.

Related: KRMA-693 (Tahoe window chrome) and KRMA-512 (Edit window surface hierarchy).
