## Objective

The persistent photo-analysis cache must only satisfy a request whose analysis level (stage coverage) it actually covers.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`PhotoAnalysisCoordinator.analyze` (`Models/PhotoAnalysis/PhotoAnalysisCoordinator.swift:108`) includes `level` in the in-flight key but builds the disk-cache key from source identity and analysis version only. Any cached result returns immediately. The stage registry (line 471) differs between fast, standard, and detailed; detailed asks for extra kinds and preview-quality masks.

Probe: seed a valid global-only result, request detailed: `detailedRequestReturnedGlobalOnly=true requestedMaskStages=0`. A standard Auto analysis can therefore satisfy a later detailed masking request without running its additional stages, and a result persisted after optional-stage failures blocks retries.

## Acceptance criteria

- [ ] A cached result is reused only if its recorded stage/quality coverage satisfies the requested level; missing stages are computed and merged into the stored result.
- [ ] Coverage is persisted explicitly (levels are not strictly nested, so a simple level-in-key is acceptable only if documented as the initial step and covers all current levels).
- [ ] A transient optional-stage failure does not permanently mark a stage as done. Retry is bounded with backoff, and unsupported masks are not retried on every request.
- [ ] Tests assert requested provider stages, not just that a result returned: fast -> detailed, standard -> detailed, detailed -> standard, relaunch with an on-disk cache, concurrent levels, and failure followed by success.
- [ ] Existing `PhotoAnalysisCoordinatorTests` pass; the cache version policy is updated if the stored format changes.
