## Objective

Change the unified Export experience into two explicit steps: configure the export first, then choose the destination folder.

## Context

In the current packaged build reviewed with `scripts/app-store-build.sh`, Export uses the selection-aware workflow completed by KRMA-1033. That work unified one-photo and multi-photo requests and put the destination picker and settings in a shared flow. The current folder chooser also hosts the export accessory, so users choose output format and naming while deciding where to save. The requested interaction is a deliberate two-step flow: first review the exact photos and configure output, then choose a folder.

Keep the target-resolution contract from KRMA-1033: export the explicit Library selection when one exists, otherwise export the active photo. Do not widen a one-photo target to the collection. Preserve the existing format, metadata, Photos-delivery, sharpening, and filename-policy behavior as applicable; this ticket changes the setup interaction and ownership of the settings, not render semantics.

KRMA-1024 and KRMA-1025 contain the existing accessory layout and batch-naming decisions. Reuse their intended controls and preferences instead of introducing a second set of export settings.

## Acceptance criteria

- [ ] Step 1 presents the exact export target set with a clear count and enough per-photo identity (at minimum filename/name and a thumbnail or equivalent visual cue) for the user to confirm what will be exported. A large selection remains navigable without eagerly loading full-resolution image data.
- [ ] Step 1 contains all applicable export settings, including format, compression/quality where the format supports it, metadata/location, output sharpening, Photos delivery when supported, and naming controls. Format-dependent settings are enabled, disabled, or explained accurately.
- [ ] Step 1 previews or otherwise makes the output naming rule clear for one and multiple photos, including any Look/prefix/suffix behavior and the selected format extension.
- [ ] A clear Continue action opens Step 2. Step 2 selects a destination folder with the native macOS folder chooser and does not repeat the settings accessory.
- [ ] Backing from Step 2 to Step 1 preserves the chosen options and target set. Cancelling either step starts no export and writes no files; export starts only after a folder is confirmed.
- [ ] The final export still uses each selected asset's own edit and Look, preserves collision-safe naming, and reports/cancels batch work as it does today.
- [ ] Existing export preferences remain consistent across subsequent exports. The two steps work for a single active photo and an explicit multi-photo selection without changing target-resolution semantics.
- [ ] Add focused regression coverage for step transitions, option persistence/mapping, cancellation, target count, and one-photo versus multi-photo behavior. `swift build` is warning-free; run the appropriate CI lane(s) for changed UI surfaces.

## Implementation notes

Keep the settings model independent of the folder panel so the same configuration can be reviewed before a destination exists. The folder picker should receive only the chosen folder and then start the already-resolved export request. Follow the current coordinator ownership boundaries in `docs/APP_ARCHITECTURE.md`; avoid duplicating rendering or filename policy in the view layer. If the existing native sheet presenter cannot support the desired step transition cleanly, add a narrow presentation seam rather than moving export orchestration into a view.

Related: KRMA-1033 (unified selection-aware flow), KRMA-1024 (settings accessory), KRMA-1025 (batch naming).
