## Objective

Photos imports never produce repeated, meaningless names. When the original filename is unavailable, the app derives a unique, meaningful name instead of "Photo 1", "Photo 2", and so on.

## Context

`PhotosImportCoordinator.swift` (around line 167) and `PhotosImportReviewCoordinator.swift` (around line 51) name each item with `provider.originalFilename(for:)` (PhotoKit `PHAssetResource`) and fall back to `"Photo \(selection.ordinal + 1)"`. The ordinal restarts at 1 for every import, so every import batch produces the same names, and the review tile tooltips, library entries, and export names all repeat.

Reported by the user in a `swift run` build, where PhotoKit authorization is probably missing (see KRMA-991), so every item took the fallback. The fallback can still be hit in the packaged app when access is limited, the asset has no resource, or the user denies access, so it needs to be sound regardless of KRMA-991.

## Acceptance criteria

- [ ] The fallback name is unique across imports. Options to weigh and record: capture date/time from the picked file's metadata (for example `Photo 2026-10-15 14.32.07`), the picker item's suggested name or content type extension, or a per-library counter. Pick one, say why.
- [ ] Two imports of different photos never get the same name. Two items from one batch with the same timestamp are disambiguated deterministically.
- [ ] The review sheet and the library show the same name for an item.
- [ ] When the real original filename is available, it is still used.
- [ ] Unit tests cover the naming (real filename, metadata date, same-second collision, no metadata).
- [ ] `swift build` is warning-free and `scripts/ci-tests.sh fast` exits 0. Swift 6 mode stays clean.

## Implementation notes

- Related: KRMA-991. If it turns out PhotoKit access is the only reason names fall back, still keep this fix so a denied or limited permission does not produce duplicates.
- Do not run `scripts/run-kromora-capture.sh`. Preserve unrelated working-tree changes.

### Comment — claude @ 2026-10-19T01:22:48.595Z

Chose capture date from PHAsset.creationDate (fallback: batch import time) formatted 'Photo yyyy-MM-dd HHmmss', since it is meaningful and differs per import; a per-library counter needs durable state and shifts names. Same-second collisions get ' 2', ' 3' in selection order. Time uses no dots because OriginalFileTypeCheck would read '.07' as an extension. Names are resolved once (PhotosImportNaming.resolve) and stamped on PhotosImportSelection so review, import, and library agree. Real filenames still win.
