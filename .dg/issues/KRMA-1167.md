## Objective

Give the analysis and mask disposable caches an application-level budget and make per-asset deletion cheap.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`PhotoAnalysisCache` and `MaskStore` write per-key files with no byte, age, or entry policy. Source, provider, and analysis-version changes leave old variants. A 60-megapixel Float32 mask alone is about 240 MB before transient copies. `PhotoAnalysisCache.remove` (`Models/PhotoAnalysis/PhotoAnalysisCache.swift:163`) and `MaskStore.remove` (`Models/PhotoAnalysis/MaskStore.swift:117`) each enumerate the whole cache and decode JSON to find one asset's records; deleting many photos repeats this per asset. Legacy mask metadata can contain an inline float array, making the "metadata" scan expensive. Code-confirmed; no measurements.

## Acceptance criteria

- [ ] Entries are organized per asset or covered by a rebuildable ownership index so a batch delete is one bounded traversal.
- [ ] Byte and age caps with background cleanup of stale-version and orphan entries, yielding to visible work. Never evict saved recipes or canonical originals.
- [ ] Large binary reads are bounded before allocation; corrupt legacy entries and interrupted two-file writes are handled without crashing or leaking.
- [ ] Tests (operation-count based): deleting a large selection does not decode every record per asset; cap enforcement; stale version cleanup; corrupt/legacy entry.
- [ ] Record disk plateau and cleanup latency in the ticket for a repeated export-quality masking session across many photos.

## Implementation notes

- Do not change mask precision or quantize without a quality comparison; that is out of scope here.


### Comment — claude @ 2026-11-03T22:24:41.864Z

Implemented in cdb78534. Layout: Masks/ and PhotoAnalysis/ now hold one directory per asset (hash of the portable asset UUID), so a single or batch delete is one removeItem per asset with no enumeration or JSON decode (tests assert metadataDecodeCount/decodeCount == 0). New Sources/KromoraKit/Models/PhotoAnalysis/DiskCacheMaintenance.swift: DiskCacheBudget (masks 2 GiB/30 d, analysis 128 MiB/90 d), a one-traversal DiskCacheTrimmer (legacy flat files, interrupted/orphan files after 1 h grace, other AnalysisVersion, superseded provider/source variants unused >24 h, age cap, LRU byte cap), and bounded IO (metadata size cap, pixel-count cap, size-checked direct Float read, atomic POSIX write without a second 240 MB copy). Reads refresh recency. PhotoAnalysisCoordinator runs trim at background priority on first request and whenever >1/8 budget was written since the last trim; shutdown cancels it. Trim touches only the cache roots, never the library package. Legacy flat/inline-float entries are no longer read (disposable cache) and are reclaimed without being opened. Evidence (synthetic, not a real 60MP session; numbers from DiskCacheBudgetTests on this machine): 400 photos x 256x256 Float32 masks (256 KiB each, 100 MiB if unbounded) with a 10 MiB budget peaked at 11.0 MiB and ended at 9.8 MiB over 80 background trims (plateau at budget); trim of 1500 assets/1500 entries 0.27 s; batch delete of 1000 of 1500 assets 0.24 s with 0 decodes. Real export-quality 60MP latency was not measured (no display-bound/RAW run per CLAUDE.md). Tests: scripts/ci-tests.sh fast passed; affected suites passed; serial lane not run (no render/AppKit code touched).
