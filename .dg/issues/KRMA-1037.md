## Objective

Avoid transferring every full Photos original once during review and a second time after confirmation.

## Context

`PhotosImportReviewCoordinator.inspect` calls `transferData` to check membership and file type for each selection. After confirmation, `PhotosImportCoordinator` calls `transferData` again for each chosen item. Since KRMA-1031 changed this provider to retrieve the original `PHAssetResource`, large RAW and iCloud-only assets can incur two full transfers and two temporary-file writes, including assets the user later deselects.

## Acceptance criteria

- [ ] Review and import do not fetch full original bytes twice for an item that is imported.
- [ ] Cancelling review or deselecting an item does not retain large payloads or leave temporary files behind.
- [ ] Provider injection, membership detection, mismatch warning, and the review selection behavior remain covered by deterministic tests.
- [ ] A test demonstrates one original-resource transfer for a confirmed item; the transfer strategy remains bounded for large RAW batches.

## Implementation notes

### Prior counterpoint verification — blocker (resolved)

The provider retains transfers only while the cumulative file size stays at or below `PhotosPickerImportProvider.retainedByteLimit` (2 GiB). For any confirmed item whose review transfer crosses that ceiling, `inspectionData` deletes its file; `transferData` then downloads that original from `PHAssetResource` a second time. This fails the first acceptance criterion for large RAW batches even though it bounds retained disk use.

The new one-transfer test uses `RetainingPhotosProvider`, whose test implementation itself retains and reuses the payload. It verifies the coordinator contract but does not exercise the production provider's 2 GiB behavior or prove the production transfer count. The bound/overflow case also has no deterministic test.

Required rework: reconcile the no-repeat requirement for every confirmed item with bounded retention for large batches. Make the retention/transfer policy testable and verify that production policy preserves the single-transfer guarantee for confirmed items while staying within its declared bound. If those guarantees cannot both hold, resolve the acceptance criteria explicitly before handoff rather than silently allowing duplicate transfers above the ceiling.

Verification to clear: add deterministic coverage that exercises the production retention policy at and beyond its bound, including a confirmed item beyond the bound, and demonstrates the chosen bounded strategy without a second original-resource fetch; retain the existing cancellation, deselection, membership, mismatch, and selection tests. Rerun `swift test --filter PhotosImport`.

Resolution in `d870fe1a`: extracted `PhotosReviewTransferCache` as the production retention policy and stopped review transfers once its byte budget is held. Later selections stay uninspected and are fetched once at import if confirmed. `PhotosReviewTransferCacheTests` exercise the limit and crossing case. The uninspected review state is tracked in child KRMA-1038.
