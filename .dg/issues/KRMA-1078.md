## Objective

When the user changes photos with the Info inspector open, visibly animate the displayed histogram
from the previous photo's distribution to the newly selected photo's distribution.

## Context

The Info inspector keeps the previous histogram visible while the next photo is prepared. Once the
new histogram is accepted, the graph currently appears to jump to the new shape instead of
transforming between shapes. This is noticeable during ordinary photo-to-photo navigation and makes
the chart feel disconnected from the transition in the main preview.

KRMA-685 (done) implemented histogram retention and intended animation, but its verification only
checked that the chart view had `Animatable`/`VectorArithmetic` wiring and an `.animation` modifier;
the report explicitly says animation timing and rendered interpolation were not tested. This ticket
is a follow-up to verify and repair the visible behavior, not a request to repeat histogram
retention or stale-result fencing.

Current code to inspect:

- `Sources/KromoraKit/Views/InfoInspectorView.swift` applies an animation when `histogram` changes.
- `HistogramChart` exposes `HistogramPlotValues` as `animatableData`, stores setter values in
  `@State animatedValues`, and draws the RGB/luma/channel curves from that state. Confirm that the
  value being interpolated by SwiftUI is the value actually read by `Canvas` on each animation frame.
- Waveform, parade, and vectorscope draw directly from `data.samples`; decide and implement an
  intentional transition for these modes too, since they are options in the same chart.
- `AppViewModel` retains the prior histogram during source selection, and
  `PreviewAdmissionCoordinator` rejects stale histogram results. Preserve these behaviors.
- `Tests/KromoraKitTests/PreviewCutoverTests.swift` covers retention and stale-result rejection but
  does not establish that the plotted shape visibly changes through intermediate values.

Reproduce with two photos whose histograms have clearly different shapes (for example, a dark
high-contrast image and a bright image). Keep the Info inspector open and step between them. The
expected result is a continuous transformation after the selected photo's accepted histogram is
ready, not an instantaneous replacement. Respect Reduce Motion.

## Acceptance criteria

- [ ] When switching photos with a histogram already visible, keep showing the previous plot while
      the selected photo's histogram is pending; begin the transition only after the current photo's
      histogram is accepted.
- [ ] In RGB, Luma, Red, Green, and Blue modes, the plotted curves visibly interpolate from the
      previous normalized bins to the new normalized bins over the transition. The `Canvas` must
      draw the interpolated values at intermediate frames, then settle exactly on the new data.
- [ ] Waveform, Parade, and Vectorscope modes also transition without an abrupt jump. Use a suitable
      continuous transition for sample-based plots rather than implying that unrelated pixels from
      two photos correspond point-for-point.
- [ ] Rapid navigation never shows an obsolete result or animates toward an obsolete photo; after
      navigation settles, every mode represents the currently selected photo's histogram/samples.
- [ ] Reduce Motion disables the transition while preserving immediate correctness of the final
      plot.
- [ ] Add regression coverage that proves histogram plot values at an intermediate animation
      fraction differ from both endpoints and that the terminal values equal the accepted target.
      Add or update presentation coverage for stale results and mode transitions where the existing
      test seams permit it.
- [ ] Manually verify the visible transition on a supported macOS build using two deliberately
      different histograms, including the default RGB mode and at least one sample-based scope mode.

## Implementation notes

Keep rendering on the existing `HistogramChart`/Canvas path and retain the current source/display
revision admission checks. Prefer making the in-flight animatable value the direct source of plotted
geometry instead of routing SwiftUI's animation setter through state that the Canvas may not observe
as its interpolated value. Keep scope-mode transition behavior explicit because those plots are
derived from bounded image samples rather than the four 256-bin channel arrays. Do not alter
histogram calculation, normalization, or photo-selection policy unless needed to make this visual
transition correct.

Related issue: KRMA-685 (completed; establishes the intended retention and animation behavior).
