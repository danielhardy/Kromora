## Objective

Library query sorting must not run on the main actor, and a foreground query must not wait behind a background planner's sort.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`orderedEntries` (`Models/LibraryQueryController.swift:712`) filters and sorts the whole projection on a cache miss; the synchronous query setters in `PortableLibrarySession` call it on the main actor. The one-query cache is bounded and fine. But `entries(for:build:)` (line 618) holds an unfair lock for the entire build, and copies share the cache, including the controller used by the background idle-warm planner. A foreground query can wait on a background sort. Code-confirmed; hitches not profiled.

## Acceptance criteria

- [ ] Query order is prepared from an immutable projection off-main and installed tagged with query and index generation; stale results are discarded.
- [ ] No sort or filter runs while holding a lock that UI callers acquire; critical sections are bookkeeping only.
- [ ] Selection publication stays coherent while preparation is in flight (no empty or mismatched grid flash).
- [ ] Tests: reverse-completing query requests; idle planner overlapping a sort change; index update during preparation. A main-actor heartbeat test proves the main actor is not blocked by an in-flight background sort.
- [ ] Record a Release main-thread trace or timing for a sort-order change at a large library size (before/after).

## Implementation notes

- Depends in practice on the lookup map and no-op rebuild tickets for good numbers, but is not blocked by them.

### Counterpoint verification blocker

The query-change path passes the focused checks, but the objective is still violated after index-generation changes. `LibraryBrowsingCoordinator.reloadPortableWindow` and `mergeCommittedImports` synchronously call `browsingWindow`/`page`; `PortableLibrarySession.refreshIndex` replaces the query controller with one whose ordering cache is empty. These entry points run on the main actor, including launch/index-loading callbacks in `AppViewModel+Library.swift` and package-import merges. A large library can therefore still be filtered and sorted on the main actor. The implementation handoff also notes this limitation.

Before verification can pass, prepare the destination's current query off-main whenever a new index generation is published, and ensure launch reload, index rebuild, and import-merge paths consume that prepared generation before any synchronous page or selection lookup. Keep the prior visible window and selection coherent until the new ordering is ready, and discard stale generation/query completions. Add deterministic coverage for reload and merge after index replacement, including a main-actor heartbeat during a large sort and an in-flight index replacement. Repeat the Release timing against that index-update path and record before/after results.
