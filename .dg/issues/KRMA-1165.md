## Objective

Edit-history refreshes must publish one coherent snapshot and ignore results from superseded invocations.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`EditHistoryCoordinator.refresh` (`ViewModels/EditHistoryCoordinator.swift:118`) calls `store.history` and `store.currentRevision` in two separate awaits. Publication only checks that the source reference still matches and shutdown has not begun. Two refreshes of one photo can publish out of order; A -> B -> A lets an old A refresh pass the check; a restore or save between the two reads can publish a history/current-pointer pair from different moments. Code-confirmed; not reproduced in a running UI.

## Acceptance criteria

- [ ] The store returns history plus the selected revision from one snapshot read, and the coordinator publishes it as one value.
- [ ] A refresh generation is invalidated by source changes and by newer refreshes; stale successes and stale failures are both ignored.
- [ ] Conflicting restore and snapshot commands are serialized or revision-fenced so completion order does not define intent. Accepted writes are still drained at shutdown.
- [ ] Tests: older success/failure finishing after newer; A -> B -> A; refresh overlapping restore and save. Assert the exact history/current-pointer pair and that the newest command wins.
