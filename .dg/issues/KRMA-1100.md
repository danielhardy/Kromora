## Objective

Introduce the session-tier `RenderDocumentIdentity` value and its equality-reusing memo on `RenderEngine`, without changing call sites yet. Child 3 of the KRMA-954 plan (`docs/RENDER_KEY_PLAN.md`).

## Scope

- New `Sendable` struct `RenderDocumentIdentity` (next to `RenderCacheKey.swift`) with deterministic SHA-256 component digests: `rawDevelop`; processing-prefix upstream (the inputs `RenderEngine.prefixDocumentHash` uses today, with and without the temperature/tint node); `localAdjustments`; the mask recipe (`RenderEngine.MaskRecipeIdentity`); per-component mask definition digests keyed by component ID; and a whole-document session key composed from the component digests. It is a distinct type, not `String`, so it cannot be passed where a durable `editHash` is expected.
- A bounded memo owned by `RenderEngine` (actor-isolated state, no locks, no escape hatches) that remembers the last few identities per `RenderSourceFingerprint`, compares each incoming component to the remembered value with `==`, reuses its digest when equal, and digests only components that differ.
- Audit test: no type reachable from `EditDocument` defines a custom `==` that ignores a pixel-affecting field (today only `CubeLUT` has a custom `==`, and it is not part of `EditDocument`). Encode the audit as a test over representative field edits.
- Extend `RenderKeyHashingBenchmark` with `identity_build_ms` for (a) cold build, (b) memoized build after an exposure tick, for each recipe.

## Acceptance criteria

- [ ] Memoized identity build after an exposure tick on the large recipe < 0.1 ms (cold build reported alongside).
- [ ] Tests: equal documents (including a JSON round-tripped copy with distinct storage) give equal identities; editing each component changes that component digest and the session key and leaves unrelated component digests unchanged; a `NaN` field never yields a reused identity; memo miss gives the same identity as a cold build.
- [ ] `RenderDocumentIdentity` is never stored in a persisted type (assert by keeping it non-`Codable`).
- [ ] No production call site changes in this ticket.

## Rules every change here must keep (KRMA-954)

- [ ] Compute immutable identity once per relevant mutation; never JSON-encode and hash the whole document on every repeated interaction.
- [ ] Session-local caches may use revision or structural keys; durable cross-launch identity keeps a stable digest (`EditDocument.editHash` bytes unchanged — the golden test stays green).
- [ ] Never persist Swift's randomized `Hasher`/`hashValue` output (no file, frame signature, edit revision, report, or string that leaves the process).
- [ ] Do not remove source, Look, or pipeline-version fences (`RenderSourceFingerprint`, Look/LUT content fingerprint, `RenderPipeline.pixelEpoch`, `LocalMaskRenderer.version`, `RenderIdentity.current`, `PresentationFrameEnvelope.storageFormatVersion`).
- [ ] Texture pooling is out of scope (KRMA-963).
- [ ] Report before/after medians from `KROMORA_RENDER_KEY_BENCHMARK=1 swift test -c release --filter RenderKeyHashingBenchmark` for the plain document **and** the large 5-brush recipe, in the handoff comment and in `docs/TESTING.md` (render-key section).
- [ ] A unit test proves equal documents produce equal keys and that an edit to each relevant field changes the key.
- [ ] `scripts/ci-tests.sh fast` and `scripts/ci-tests.sh serial` exit 0.
