## Objective

Make index-side asset ID lookups O(1) so batch operations over the library are linear, not quadratic.

## Context

Source: audit `.context/audits/2026-11-03-code-quality-audit.md` (against `b7e46d5c`); probe source and outputs are in `.context/audits/evidence/2026-11-03/README.md`. Line numbers below are from that commit and may drift.

`LibraryIndexProjection.entry(for:)` (`Models/LibraryQueryController.swift:224`) is `entries.first { ... }`. `browsingAssets(forIDs:)` (`Models/PortableLibrarySession.swift:1510`) repeats that scan per ID. Launch hints, selection validation, source resolution, and idle-warm candidate hydration all use these paths, so K lookups over N entries cost O(N*K) even when page ordering is cached. Code-confirmed algorithm; not profiled.

## Acceptance criteria

- [ ] One immutable ID -> index map is built per projection/controller generation and shared by lookups and selection validation; the ordered array remains the paging authority.
- [ ] Locating the page for a known asset uses the map rather than building and scanning successive pages.
- [ ] The map is not rebuilt per viewport callback.
- [ ] Tests (operation-count based, not wall clock): K lookups after one build do O(K) work; deletion, source replacement, copies, query changes, and duplicate-ID rejection remain correct.
- [ ] Record a Release comparison for an idle-warm planning pass and active-photo open at a realistic library size.
