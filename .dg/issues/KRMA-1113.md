## Objective

Make sure adding about 20 bundled 33^3 Look cubes does not slow app launch or Look library creation. Measure first; fix only if the measurement warrants it.

## Context

LUTLibrary.init calls BundledLookLibrary.load() synchronously when includeBundled is true, and load parses every bundled .cube as text through CubeLUT(url:). Today that is 13 cubes of 27 rows. The film-look family (see docs/FILM_SIMULATION_LOOKS_RESEARCH.md and KRMA-1103) adds about 20 cubes of 35,937 rows each, roughly 750,000 text lines parsed at launch. This has not been measured. The parser limits are 16 MB per file and 64 KB per line, so format limits are not the issue.

## Approach

1. Measure BundledLookLibrary.load() with a set of representative 33^3 cubes (generate them with the KRMA-1103 generator or an identity-plus-noise stand-in) in a release build on Apple Silicon; record the time and the thread it runs on, per docs/TESTING.md conventions. Do not use the display-bound capture harness.
2. If the cost is not noticeable (agree a budget in the ticket, for example well under the existing first-frame budget), record the numbers and close with no code change.
3. Otherwise pick the smallest fix: load bundled cubes lazily when first shown or selected, load off the main actor, or ship a binary cube resource generated at build time with the text .cube kept as the source of truth. Keep the manifest validation gate (BundledLookLibrary.validate) working for whichever format ships.

## Acceptance criteria

- Measured parse time and thread recorded in the ticket and docs/TESTING.md.
- Either a documented decision that no change is needed, or a fix with a test proving bundled Looks still load, validate and resolve by stable id.
- Existing BundledLookTests and Look selection tests pass.
- No change to Look output: the same cube renders identically before and after.

## Out of scope

The cube generator, the Look content, and category ordering.
