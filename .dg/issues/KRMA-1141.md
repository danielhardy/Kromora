## Objective

Make export succeed for a photo whose edit includes the subject mask that Auto adds, in every export format, and report the real failure to the user when an export does fail.

## Context and reproduction

Found during the KRMA-1064 16 GB qualification re-run (see KRMA-1016). Export of a photo that carries an Auto edit fails every time; the same photo unedited exports fine. Dev build (`scripts/disposable-app.sh`, Release, ad hoc signed, unsandboxed) on `65894b18`, Apple M1 Pro 16 GB, macOS 27.0.1, disposable library package, imported RAWs are copies of four real ARW files (47/82/120/122 MB) with unique trailing bytes appended.

Reproduction (clean launch, 20-RAW library, photo K64-0000.ARW, a hummingbird image):

1. Open the photo, File > Export (cmd+s), JPEG, no edits: succeeds, 4.5 MB file written, status shows the export complete.
2. Same photo, press Shift+A (Apply Auto Edits, "5 coordinated controls"), then export as JPEG: fails within about 1 s, no file is written, status bar shows only `Exported 0 of 1 (1 failed)`.
3. Reproduced four times on this build. An earlier export to TIFF of an Auto-edited photo also failed. A night photo earlier showed a similar "subject mask could not be analyzed" message in the editor.

Exact error (captured with temporary stderr logging in the two `performBatchExport` catch blocks, since reverted; nothing reached the unified log):

```
export failed K64-0000.ARW: The subject mask could not be regenerated: processingFailed | The operation couldn't be completed. (KromoraKit.LocalMaskResolutionError error 2.)
```

That is `LocalMaskResolutionError.providerFailure(target: .subject, reason: "processingFailed")`, wrapping an `ImageError.processingFailed` from the mask provider (`Sources/KromoraKit/Models/LocalMaskRendering.swift`, provider errors wrapped with `String(describing:)`).

Two problems:

1. Export of an Auto-edited photo fails (the product bug).
2. The per-item reason is shown in a status message ("Skipped <name>: ...") and then overwritten by the final `Exported N of M (K failed)` summary, so the user never sees why. This is why the failure needed instrumented diagnosis.

## Suspected cause (not confirmed)

`AnalysisImageFactory.make` (`Sources/KromoraKit/Models/PhotoAnalysis/AnalysisImage.swift`, around line 124) throws `ImageError.processingFailed` when `source.nativeExtent` has a non-finite or sub-1 pixel width or height. `ExportCoordinator.sourceAccess(for:)` builds the export `ImageSource` with `ImageSource.resolve(url: resolved, nativeExtent: .zero)`. If the zero extent reaches the analysis factory when the subject mask is regenerated at export, this is exactly the observed error. No test or debugger confirmed that this path is the one taken; verify before fixing, and check whether the interactive editor path passes a real extent.

## Not established

- Whether non-subject masks (linear/radial/brush) regenerated at export hit the same path.
- Whether this affects the signed sandboxed build (only the unsandboxed dev build was run).
- Whether it reproduces with a distinct real RAW rather than the four trailing-byte copies. The failure needs only an Auto edit, so the fixtures are unlikely to be the cause, but that is not proven.
- Whether the batch export of several photos fails per item or aborts.

## Implementation boundaries

No fallbacks for older macOS or Intel. Do not run `scripts/run-kromora-capture.sh`. Use generated or disposable fixtures and never modify a user's active library.
