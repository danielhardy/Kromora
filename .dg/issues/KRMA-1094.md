## Objective

A photo with automatic Heal spots takes noticeably longer than any other photo to produce its histogram and refresh its preview. Make the automatic source pick a one-time cost per photo and spot set, not a cost on every render.

## Context

Reported on `DSC04485.ARW` (Sony ILCE-7RM3A, 7952×5304). Its histogram and related panels are much slower than any other photo in the library.

What was ruled out, from measurement on the reporter's machine:

- **The file.** Same body, sensor, and file size (about 85 MB) as the other A7R III ARWs in `~/Downloads/samples/images`.
- **RAW decode.** `CIRAWFilter` graph plus a 512 px render was about 0.14 s for DSC04485 and for the other A7R III files. Setting this photo's exposure (+3.28), white balance, highlight recovery, luminance noise reduction and EDR amount did not move it.
- **The histogram code.** `RenderEngine.histogram(source:document:...)` re-runs the preview graph through `buildImage`, then tallies a 512 px RGBA8 buffer. Anything slow in `buildImage` is slow in the histogram.
- **Other edit math.** The latest stored edit (revision 201 of asset `D1650CC7-F4C6-490E-A38A-9C65B11A15BB`) has exposure +3.28, texture 23, clarity 14, red/green/master curves and a cyan saturation tweak. None of that is unusual cost.

What is unique to this photo: it is the only one of the 17 assets in the library whose latest edit has Heal spots. It has four, and none has a stored `source`:

- two sit at the default centre `(0.5, 0.5)`, probably stray placements that still count as non-identity because they are visible, opaque, and have a sample;
- two are near `(0.569, 0.336)` and `(0.558, 0.355)`.

Why that is expensive (read from the code, not yet profiled in the app):

1. `RenderEngine.buildImage` calls `resolvingAutomaticRetouchSources` (`RenderEngine.swift`, around line 1504 and 1628) whenever `resolveRetouchFills` is true. It defaults to true, and `histogram()` uses the default. Other call sites pass `request.maskResolution == .resolved && request.quality != .interactive`.
2. That function loops over every spot with `source == nil` and awaits `pickRetouchSource` for each one, serially. Each spot's pick sees the earlier picks in `resolved`, so the order matters.
3. `pickRetouchSource` runs a CPU scan of the 1024 px analysis proxy (`RetouchSourcePicker.candidates`, limit 24, ring search plus a per-point score), then `retouchAnalysisCrop` develops the RAW at `.neutral` and `.full`, renders a crop to RGBA8, and `RetouchSourcePicker.refining` re-ranks.
4. Only the proxy bitmap is cached (`retouchAnalysisCache`, keyed by source fingerprint). The chosen `RetouchSource.auto(offset:rank:)` is not cached and not written back to the stored edit, so the whole search repeats on every histogram, preview, and thumbnail build while the document still has `source == nil` spots.
5. For RAW, `developedSourceForBuild` bypasses the developed-source cache and goes through the single-entry interactive `CIRAWFilter` session. A neutral request followed by the photo's own `rawDevelop` request may reconfigure that session each time. This is a suspect to confirm, not a finding.

In an isolated script a full-resolution crop render of this file took about 0.02 s, so the repeated CPU scan or the session reconfiguration is the likelier cost than the demosaic. First step is to say which.

## Acceptance criteria

- [ ] A measurement on `DSC04485.ARW` with its current stored edit records where the time goes (candidate scan, neutral develop, crop render, refine, or RAW session reconfiguration) and the histogram-after-ready time before the change. Use a window-independent test or signposts; do not run `scripts/run-kromora-capture.sh`.
- [ ] After a photo's automatic Heal sources are resolved once, later histogram, preview, and thumbnail builds for the same source and spot set reuse the result and do not call `pickRetouchSource` again. A test counts picker invocations across at least two builds.
- [ ] The cache key covers everything that changes the pick: source fingerprint, each spot's region, feather, and id, the spot set (picks depend on the other spots), and the picker's algorithm version. Moving, adding, removing, or hiding a spot re-picks only what changed.
- [ ] A manual source offset is still preserved exactly, and an unchanged document renders identical pixels before and after the change (the existing retouch render tests still pass).
- [ ] Histogram-after-ready on `DSC04485.ARW` is in line with the other A7R III photos in the same measurement. Record the before and after numbers in the issue.
- [ ] Decide, and record the decision in the issue, whether the picked source is persisted into the edit revision. Persisting makes a reopened photo instant, but it changes the stored recipe and the revision history, so it must not be done without an explicit call. An in-memory cache is enough to close this ticket.
- [ ] No change to what a Heal spot looks like for the same inputs. No `@unchecked Sendable`, `nonisolated(unsafe)`, or `@preconcurrency`.
- [ ] `swift build` is warning-free and `scripts/ci-tests.sh serial` passes for the retouch and engine tests.

## Implementation notes

- The cache belongs in `RenderEngine` next to `retouchAnalysisCache`, bounded and reset with the source boundary, so a replaced file never reuses picks. Keep Core Image objects inside the engine; the cache holds only `Sendable` values (`RetouchSource`, offsets, keys).
- Because each pick depends on the others in the set, key per spot with a hash of the whole ordered spot set, or cache the resolved set as one unit. The second is simpler. Decide with the measurement in hand.
- Check whether the picks should also be skipped for work that does not need them: thumbnails and `.interactive` already pass `resolveRetouchFills: false`; confirm `histogram()` should render with resolved fills at all, or whether it can reuse the presented image's tally.
- Look at the two stray `(0.5, 0.5)` spots separately. If the UI can create a visible spot that was never positioned, that is a bug worth its own ticket; this ticket should not delete user data.
- Update `docs/RETOUCH.md` with the cache contract and its key.

## Non-goals

- Changing how `RetouchSourcePicker` scores candidates or which source it picks.
- Changing the Heal blend, mask, or pull/push pyramid.
- Reworking the single-entry RAW session.
- Running the display-bound capture benchmark.
