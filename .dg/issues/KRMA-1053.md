## Objective

Ensure repeated or partially completed recovery preserves the last committed files and can finish safely after every rollback interruption.

## Context and reproduction

Finding 1 of the October 19 review was reproduced against the compiled production transaction code. rollback moves a backup back to its target but does not durably mark that restoration. A retry sees publicationState == published, no backup, and an existing target, then deletes the restored target. A crash between restoration and journal cleanup, a durability failure after restoration, or failed journal deletion can leave this state.

Reproduce with a disposable package: write old State/value.txt; begin a transaction with a .publish fault injector; stage new bytes; let commit fail at publication. Read its journal, remove the replacement target, and move its backup onto the target, leaving the journal. These are rollback's actual mutations up to the interruption. Call recover again. Before the fix, the old file exists before retry and is absent afterward. Package membership shards and asset records use this transaction layer, so the same ambiguity affects canonical data.

Use the validated journal representation produced by KRMA-1052. Do not regress its path restrictions while fixing recovery state.

Source review: .context/2026-10-19-release-readiness-review.md (reviewed bb01e0c374fb; re-read current code because subsequent work may have landed).

## Acceptance criteria

- [ ] Convert the reproduced state into a deterministic regression that fails before the fix and preserves the restored old bytes after the fix.
- [ ] Define and implement resumable rollback state for files, journalled moves, and removals; the absence of a consumed backup must not mean the restored target can be deleted.
- [ ] Exercise interruption before/after each restore mutation and journal/directory durability boundary, including one restored file followed by failure on another; repeated retries converge to the same pre-transaction state.
- [ ] Exercise journal-cleanup failure after restoration. A retained journal cannot delete the already-restored target on a subsequent open.
- [ ] Keep committed-journal cleanup, newly created-file rollback, mixed replacement/move/removal rollback, lease ownership fences, and prior publication-fault tests correct.
- [ ] Do not discard journals/backups on a recovery error. Use explicit test fault seams rather than process-kill timing or non-disposable user data.
