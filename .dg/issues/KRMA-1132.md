## Objective

Show where a photo's colors sit relative to the sRGB and Display P3 gamuts, in the Info inspector's Image area. A small chromaticity plot (sRGB and P3 triangles over a density of the image's pixels) plus a number: the share of pixels outside sRGB and outside P3. This makes the P3 decision visible per photo instead of a number in a ticket.

## Context

KRMA-1114 measured the share of pixels outside sRGB on local camera files: 0% in two Sony ARWs, 0 to 4.39% in the iPhone DNGs, 1.81% in the HEIC. Those figures came from a one-off measurement; the app has no way to show them. Users with a P3 display or a saturated subject cannot tell whether P3 matters for a given photo.

Existing pieces: `InfoInspectorView` (Info tab: identity, `InfoAnalysisSection`, edit history, metadata), the "Image" metadata section in `ImageMetadata.swift`, and `HistogramData` / `RenderEngine+Histogram.swift`, which tally a bounded RGBA8 sample of the presented pixels. `WorkingSpace.current` is Display P3 with extended-range values kept alive between stages.

Design constraints and open decisions:

- The histogram's RGBA8 sample is encoded in the output space, so it can show "outside sRGB" (convert P3 to extended sRGB and test for components below 0 or above 1) but cannot show colors beyond P3. Decide whether that is enough, or whether the gamut tally should come from a float sample of the working-space image (extended range, bounded size) for a RAW wider than P3. Keep Core Image graph construction inside `RenderEngine`; only Sendable values (a small binned grid plus counts) cross to the UI.
- Plot space: CIE 1976 u'v' is more perceptually even than xy; either is acceptable. Bin pixels into a fixed grid (for example 64x64) and draw density; no per-pixel drawing.
- Cost: compute only when the Info tab is visible, reuse the retained presentation sample where possible, and never block the render path. Do not run the display-bound capture harness.
- Which image: the edited (rendered) result, not the source. Say so in the label; consider a source-versus-edited toggle only if cheap.
- Edit state matters: a Look or saturation change moves pixels in or out of sRGB, so the plot updates with the edit like the histogram does.

## Acceptance criteria

- [ ] A gamut view in the Info inspector's Image area (collapsed by default if it costs more than a histogram refresh), showing sRGB and Display P3 triangles and the image's pixel density.
- [ ] Shows the percentage of pixels outside sRGB and outside P3, matching an independent calculation on a generated test image (for example an all-in-sRGB patch set reads 0%, a P3-only saturated green patch reads its known area).
- [ ] The tally is a pure, Sendable, unit-tested function over a pixel sample; a synthetic image in sRGB, P3-edge and out-of-P3 patches covers it.
- [ ] Updates with edits and image switches without stalling slider interaction or the Info tab; no new work when the tab is hidden.
- [ ] Reproduces the KRMA-1114 figures on the local Sony and iPhone fixtures within a stated tolerance (opt-in RAW lane), or the ticket records why they differ.
- [ ] Accessible: the plot has a text alternative giving the percentages, and works in light and dark appearance.
- [ ] docs/ENGINEERING_GUIDE.md or docs/TESTING.md notes the sample source and cost.

## Out of scope

Soft-proofing, gamut warning overlays on the canvas, and gamut mapping. A canvas overlay marking out-of-sRGB pixels is a natural follow-up.

### Counterpoint verification — codex @ 2026-10-26

**Blocking acceptance gap:** The issue requires the share of edited pixels outside both sRGB and Display P3. The view only passes `HistogramData.samples` to `GamutTally(displayP3Samples:)`. Those are 8-bit Display P3 values bounded to the P3 gamut, so that initializer sets `measuresBeyondP3` to false and always reports zero outside-P3 pixels; the UI confirms that the percentage is unavailable. `GamutTally(linearDisplayP3:)` is unit-tested but has no production caller or sample producer. The core outside-P3 requirement is therefore not implemented.

**Required change:** Produce a bounded extended-linear Display P3 sample from the edited render on demand for the visible, expanded Info gamut disclosure, using `RenderEngine` for Core Image work. Feed its Sendable pixel values to the tally and show measured outside-sRGB and outside-P3 percentages. Keep this asynchronous and tied to the current edit/sample so image switches and edits refresh the result, and hidden/collapsed Info UI schedules no new work.

**Verification required:** Exercise the production sample path with a generated image containing in-sRGB, P3-only, and beyond-P3 patches; compare both percentages against independent expected areas and verify the extended sample retains beyond-P3 values. Verify image/edit changes refresh the result without blocking interaction and that hidden/collapsed UI does not request a sample. Run `scripts/ci-tests.sh optional` with the local camera fixtures and compare the Sony/iPhone results to KRMA-1114 within a stated tolerance, or document a concrete processing/sample difference that explains any mismatch.
